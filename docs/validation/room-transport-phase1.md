## 实现范围

静态地图在每条 WebSocket 连接首次发送，后续引用缓存；强盗位置仍随每次状态更新发送。命令 HTTP 响应可协商为包含版本号的 ACK，避免向操作者重复返回整份房间。正常启动直接使用 WS 初始快照，缺失时保留 HTTP 恢复路径。

前端收到的仍是完整 `RoomView`。接收层统一处理版本顺序、座位凭据变更、ACK 与推送先后顺序及重连动画基线。旧客户端和旧服务端仍可使用完整快照协议。游戏规则、渲染组件、结算数据和数据库结构没有因本阶段优化而改变。

动态状态、历史记录和效果列表仍按完整快照下发。历史/效果增量化留待独立设计，本阶段没有引入通用差量合并或事件重放。

## 完整对局实测

在独立临时本地服务上，分别用旧协议和新协议跑四人、六人各一局到胜利结算，共四次完整运行。种子均为 `20260820`，胜利目标为 10 分；四人局各 278 次合法命令，六人局各 137 次。使用真实 HTTP 和每个座位的真实 WS 订阅，服务器执行规则；没有修改资源、骰子或游戏状态来加速胜利。使用临时内存数据库，未操作用户现有房间。

以下 WS 数据是所有座位合计、已协商 `permessage-deflate` 的实际接收字节数，包含 WS 帧头，不含 TCP/IP 头、建连握手及操作前初始快照。MB/KB 使用十进制。HTTP 数值是响应 JSON 大小，不是生产代理压缩后的网络用量。

上传增加约 21 B 是显式 `responseMode: "ack"` 协商字段；上传本来就只有命令、凭据及版本等少量数据，下行重复快照是此次主要收益来源。初次连接和地图变化仍需完整地图，重连也不会依赖上一连接的缓存。

新旧协议每个座位、每次更新还原后的完整视图均计算摘要对比，四人和六人两组全部一致，包含最终结算。随机生成的房间/玩家标识归一化为对应座位，时钟时间字段排除比较；其余完整数据参与比较。每份解码视图另与服务端当前权威投影比较，均通过。两组前后命令数量、类型和胜利座位也一致。

## 回归结果

- `pnpm validate`：通过，包含类型检查、281 项单元测试与构建。game-core 60、protocol 37、server 51、web 133 项。
- `pnpm test:e2e`：最终全量通过，86 项，Chromium，约 2 分钟。
- 新增协议测试覆盖四/六人地图还原、强盗移动、地图更换、缓存失效、重连及私密手牌隔离。
- 新增服务端测试验证 ACK 不产生额外私有投影、幂等重试、版本冲突和旧式完整响应兼容。
- 新增客户端测试覆盖 ACK/推送顺序、超时和断线补拉、旧响应不能覆盖新状态、同游戏版本的房间元数据更新、账号/座位变更隔离及重连不重播旧动画。
- 新增桌面及手机浏览器端流程覆盖初始快照、ACK 等待、丢推送恢复、迟到消息、重新连接和强盗位置；另有缺失地图基线后重连恢复用例。

首次全量端到端运行发现三处测试夹具/等待条件与真实时序不一致：AI 更新夹具未递增房间版本，发展卡动画夹具未提供 WS 初始快照，交易测试过早移除请求拦截。修正后先复跑失败的三例，通过后再运行上述完整 86 项。没有放宽产品断言来跳过失败。

构建仍提示现有前端主包超过 500 KB；本阶段没有处理资源包拆分。
