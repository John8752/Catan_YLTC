# 第二阶段传输优化验收

日期：2026-09-05。设计见 [ADR-0013](../adr/adr-0013-incremental-room-events.md)，比较基线为[第一阶段地图缓存与命令 ACK](./room-transport-phase1.md)。

## 实现范围

新客户端协商 `events-v2`：初次连接获取当前状态、静态地图和最近一页记录，后续只推送新产生的玩家可见记录及瞬时效果。动态游戏状态仍使用完整投影，没有引入通用对象差量。旧客户端保留原协议。

公开记录面板取消最近 30 条的展示截断。初始页和向前翻页以 50 条可读记录为目标，同一命令版本的记录保持完整，因此单页可以超过 50 条。向上滚动或点击加载入口可读取当前对局开局以来的记录；已加载记录保留，插入旧记录保持阅读位置，新增记录提供返回最新入口。

记录具有稳定 ID 和完整版本区间，客户端去重并补齐断线缺口。补页只扩展历史，不覆盖较新的游戏状态；补齐期间保留正在阅读的连续记录。重连和历史翻页不重播旧动画，ACK 丢推送恢复则按客户端最后显示的游戏版本补回尚未收到的新效果。

历史接口校验当前座位凭据、游戏实例和游标，所有内容仍经过该玩家的安全投影。房间/座位切换会清空缓存并丢弃迟到响应。游戏规则、账号结算和数据库结构不变；整局原始事件原本就保存在服务器内存，当前功能没有增加永久对局日志存储。账号继续只保存最终结算。

## 完整对局实测

使用独立临时本地服务、内存数据库、真实 HTTP 命令和每个座位的真实 WS 连接，分别运行第一阶段协议和第二阶段协议的四人、六人完整对局，共四次运行。种子为 `20260820`，胜利目标 10 分，由合法命令自动策略运行到结算，未改写资源、骰子或状态来加速胜利。

四人局每次 278 条命令、367 条原始事件、274 条可读历史，获胜者为座位 1，最终 11 分；六人局每次 137 条命令、174 条原始事件、117 条可读历史，获胜者为座位 1，最终 10 分。

另外对每个座位从最新页向前完整下载历史并校验。四人局座位 1 下载 6 页、274 条，合计 35,388 B；六人局座位 1 下载 3 页、117 条，合计 15,414 B。这是额外按需 HTTP 下载的未压缩响应体成本，没有计入上表 WS 总量；持续在线的客户端已经累积收到历史，不需要重复下载整局。

第二阶段使用实际解码器和 `RoomUpdates` 合并层，逐次将每个座位的累积历史、新效果及其余完整视图与服务端权威投影比较。历史另与从开局投影的完整记录核对，最终分页读取也逐条核对。前后所有座位的完整视图摘要一致，包含最终结算；随机房间/玩家 ID 归一化为对应座位，时钟字段排除比较。稳定警告 ID 按服务端追加顺序生成，保证同版本多条警告不受随机玩家 ID 影响。

## 回归结果

- `pnpm validate`：通过，包含类型检查、293 项单元测试和构建。game-core 60、protocol 42、server 53、web 138 项。
- `pnpm test:e2e`：最终全量 88 项通过，Chromium，包含主要手机矩阵与新增历史交互测试。
- 协议和 HTTP 测试覆盖 600 条记录完整分页、同版本大量事件不拆页、无可读记录区间、警告排序、私密发展卡投影、非法游标及替换后的座位凭据。
- 接收层测试覆盖重复/迟到消息、缺失基线、断线缺口、分页与新推送并发、座位切换、ACK 丢推送后的新效果恢复，以及旧页面不能覆盖动态状态。
- 新增桌面和手机流程验证初次只有最近 50 条且不额外拉历史、滚动锚点、重复推送、完整加载 251 条、漏帧重连、长断线自动补到 400 条、刷新恢复最近一页和失败重试。
- 旧的 30 条截断断言已更新；原有滚动窗口锚点用例改为显式模拟旧协议窗口变动，仍保留该兼容行为的验证。

构建提示前端主包 513.33 KB（gzip 160.42 KB），超过现有 500 KB 提示阈值；本阶段未处理代码包拆分。SQLite 实验性 API 提示仍存在。已加载历史的客户端内存和 DOM 会随记录数量增长，当前未采用虚拟列表；本阶段验证了数百条规模，不宣称无限记录的性能保证。
